# Очередь профилирования — задача 6

Отдельный процесс `python -m site_profiles.profile_queue` хранит состояние в
SQLite внутри `codex_work`. Он не использует production pipeline, Kafka,
диспетчерскую редактирования профилей или граф. Автоматическое применение
профилей отсутствует. Никакой сервис не устанавливается и не запускается
автоматически при переносе исходников.

## Подключённые этапы

- `discover`: задача 4 на явно заданном сохранённом корпусе, с лимитами страниц,
  URL, глубины, времени и размера выборки. Сохранённый корпус оставляет
  `uncertain`: полнота живого сайта не подтверждается.
- `markdown`: задача 5 с готовым Markdown либо генерацией по зафиксированному
  профилю. Читается `status` отчёта, а не успешный код завершения CLI.
  При наличии предыдущего discover его отчёт автоматически передаётся
  для проверки покрытия выборки.

- `control`: [задача 7](CONTROL_RUN.md) — свежая выборка HTTP/браузером, модель, DOCX и доказательства.

Порядок этапов: discover → markdown → control; можно указать только нужные.
Недоступные доказательства и ограничения предыдущего этапа сохраняются.
Подготовка/исправление YAML и смысловая приёмка остаются работой исполнителя.
Живой control требует явных ресурсных слотов и bwrap с read-only исходниками.
Произвольные команды и live-обнаружение по-прежнему запрещены; браузер/модель
разрешены только внутри фиксированного обработчика control.
Интеграция с `profile-review` остаётся задачей 8.

## Создание и запуск

Все команды выполняются из рабочей копии исходников в `codex_work`. Ниже
`python` — Python окружения проекта с установленными зависимостями.

```bash
python -B -m site_profiles.profile_queue \
  --queue /ai/projects/stroy-resurs/codex_work/queues/batch_001 init
python -B -m site_profiles.profile_queue \
  --queue /ai/projects/stroy-resurs/codex_work/queues/batch_001 add /путь/job.json
python -B -m site_profiles.profile_queue \
  --queue /ai/projects/stroy-resurs/codex_work/queues/batch_001 run --drain
python -B -m site_profiles.profile_queue \
  --queue /ai/projects/stroy-resurs/codex_work/queues/batch_001 status
```

`init` требует новый каталог. `run --drain` обрабатывает очередь, включая
отложенные повторы, и заканчивает работу после исчерпания заданий. При паузе
или недостатке свободного диска завершает доступную работу и оставляет
неисполненные задания в очереди. Возвращаемый 0 означает корректное выполнение
команды, а не отсутствие failed/exhausted — смотрите `status`.

`run` без `--drain` продолжает ожидать новые задания независимо от интерактивной
сессии при запуске под обычным менеджером процессов либо через `nohup`:

```bash
nohup python -B -m site_profiles.profile_queue \
  --queue /ai/projects/stroy-resurs/codex_work/queues/batch_001 run \
  >> /ai/projects/stroy-resurs/codex_work/queues/batch_001/dispatcher.log 2>&1 < /dev/null &
```

Команды `pause` / `resume` сохраняют флаг в SQLite. Пауза запрещает новые старты;
текущие попытки заканчивают работу. SIGTERM/SIGINT также прекращают новые старты
и дожидаются ограниченных по времени работников. `resume` не создаёт процесс:
если `run --drain` уже завершился, его нужно запустить снова.

## Manifest задания

```json
{
  "version": 1,
  "url": "https://factory.test/",
  "profiles": "candidates",
  "label": "проверка кандидата 3",
  "stages": [
    {
      "kind": "discover",
      "manifest": "saved_corpus.json",
      "no_sitemap": false,
      "control": ["https://factory.test/catalog/pump/"],
      "holdout": ["https://factory.test/catalog/other/"],
      "limits": {"pages": 60, "urls": 10000, "depth": 5, "seconds": 120, "sample": 30}
    },
    {
      "kind": "markdown",
      "manifest": "markdown_manifest.json",
      "model_char_limit": 100000
    }
  ]
}
```

Пути относительно job.json. Форматы вложенных manifest описаны в
[STRUCTURE_DISCOVERY.md](STRUCTURE_DISCOVERY.md) и
[MARKDOWN_VALIDATION.md](MARKDOWN_VALIDATION.md). Эталон Markdown задаётся
независимо от правил проверяемого профиля. Вход модели должен быть захвачен
после реальной обрезки/обработки таблиц; симуляция не подтверждает этот этап.
PDF/DOCX не используются для получения характеристик.

При постановке копируются исходники обработчиков и адаптеров, всё дерево
кандидатов/общих правил, JSON manifest и все перечисленные входные файлы.
Внутренние ссылки manifest переписываются на сохранённые копии. Фиксируются
SHA256, Python и версии установленных пакетов. Идентификатор задания — хеш
снимка и лимитов. Повторная постановка того же задания возвращает прежний id;
завершённые этапы заново не выполняются. История повторной подачи сохраняется.

Изменение кода, правил, HTML/Markdown или лимитов создаёт другое задание.
Исходные файлы после постановки можно дорабатывать: уже поставленное задание
использует собственный снимок. Изменение самого снимка или окружения блокирует
его запуск с причиной. Окружение не копируется автоматически; при его обновлении
нужно восстановить прежнее окружение либо поставить новое задание.
Исправленный кандидат/входы — новое задание. Для сознательного повтора тех же
данных после внешней диагностики задайте новый `label` с причиной повтора;
история прежнего задания сохраняется.

## Состояния и восстановление

Задание: `pending → running → pending` для следующего этапа либо конечный статус:

- `complete`: все подключённые этапы дали pass. Это **не принятие профиля**,
  не его внедрение и не подтверждение полного каталога.
- `review`: этапы выполнены, хотя бы один оставил uncertain.
- `failed`: устойчивый дефект, нарушение изоляции/целостности, неверный вход
  или fail проверки качества; автоматического повтора нет.
- `retry`: временная ошибка, авария процесса или тайм-аут; сохранена дата повтора.
- `exhausted`: исчерпан лимит попыток этапа либо активного времени задания.

Для каждой попытки сохраняются id, этап, номер, время, каталог, результат и
причина ошибки. `events` содержит историю переходов. Временные TimeoutError,
ConnectionError и EAGAIN/ETIMEDOUT/ECONNRESET отделяются от ошибок входных данных
и сравнения. Ненормальный выход без завершённой квитанции повторяется ограниченно.
Сеть выключена для discover/markdown. Для control действует периметр сайта/модели.
Незавершённый control не повторяется автоматически: запрос модели мог быть
выполнен. Сохраняется пакет неполноты, задание получает review.

Транзакция SQLite фиксирует running до старта процесса. Работник сохраняет
артефакты, receipt.json и контрольный маркер receipt.ready; только затем
диспетчер фиксирует завершение. После аварии:

- полностью записанная квитанция с верными SHA256 принимается в ту же попытку;
- незаконченная попытка получает причину и повторяется в новом каталоге;
- повреждённая завершённая квитанция/артефакт блокирует задание;
- уже завершённые этапы не повторяются; их артефакты проверяются перед продолжением.

В одной очереди работает один диспетчер, но несколько работников. Flock
наследуется работниками: новый диспетчер не захватит очередь, пока жив сирота
старого процесса. Собственный таймер работника завершит его даже при гибели
родителя. Блокировка освобождается ядром, удалять lock-файл не нужно.
SQLite и flock рассчитаны на локальную файловую систему одного Linux-хоста,
не на распределённый/NFS-кластер. В разных каталогах очереди лимиты независимы;
для общей нагрузки используйте одну очередь.

## Лимиты

`init --limits limits.json` переопределяет значения по умолчанию. После создания
лимиты очереди фиксированы; для другого набора создайте новый каталог очереди.

| Поле | По умолчанию | Значение |
|---|---:|---|
| workers | 2 | Одновременные процессы этапов, максимум 32 |
| per_host | 1 | Одновременные этапы одного хоста; www и основной хост объединены |
| host_delay | 1 | Минимальная пауза между стартами/после завершения этапов хоста, секунды |
| max_attempts | 3 | Максимум попыток каждого этапа, включая первую |
| retry_delay / retry_cap | 10 / 300 | Экспоненциальная задержка и её предел, секунды |
| stage_seconds | 180 | Время одной попытки; монитор диспетчера имеет запас 2 секунды |
| job_seconds | 900 | Суммарный бюджет исполнения этапов, без ожидания очереди/backoff |
| memory_mb | 2048 | RSS дерева процессов; дополнительно RLIMIT_AS без Chromium, минимум 256 MB |
| attempt_mb | 100 | Лимит файла RLIMIT_FSIZE и контроль суммы размеров файлов попытки |
| snapshot_mb | 256 | Бюджет копирования входов/исходников одного задания |
| min_free_mb | 100 | Минимум свободного диска для постановки и старта |
| browser_slots / model_slots | 0 / 0 | Явные квоты control, не больше workers |

CPU-время ограничено тайм-аутом; BLAS/OMP ограничены одним потоком. Контроль
суммарного диска периодический: возможен небольшой выход за лимит до остановки.
После сбоя без квитанции время учитывается консервативно — не более тайм-аута
попытки. Для живого control дополнительно действуют лимиты запросов, ответа
и пауза хоста из [контракта задачи 7](CONTROL_RUN.md).

## Изоляция и артефакты

```text
queue.sqlite3                  состояние, попытки, события
submissions/<id>/              неизменяемый снимок подачи
  runtime/ profiles/ assets/ manifests/ job.json environment.json hashes.json
attempts/<job>/<stage>/<n_id>/  отдельная попытка
  request.json worker.log home/ tmp/ cache/ output/ receipt.json receipt.ready
```

Проверяется расположение после разрешения symlink; выход только внутри
проектного codex_work. Дочерний процесс получает очищенное окружение с HOME,
TMPDIR и XDG_CACHE_HOME своей попытки. Python audit hook запрещает production
pipeline/загрузчик графа, удаление/ссылки и запись за пределами попытки.
Для discover/markdown также полностью запрещены сеть и subprocess. Control
имеет строго ограниченные разрешения и обязательный read-only bwrap, подробнее
в его контракте. Проверены авария и восстановление.

Это ограниченный исполнитель доверенного кода проекта, не ОС-песочница для
вредоносных Python/C-расширений и не защита от одновременного злоумышленного
изменения файлов снаружи. Произвольные пользовательские обработчики не допускаются.
Продовые карточки, индексы, профили и кэши читаются только как явно указанные
входы; записей в них, граф и Kafka нет. Control обращается к указанной модели
и сайту в заданных лимитах. Исходные материалы,
неудачные попытки и старые версии сохраняются, автоматической очистки нет.
Оператор должен учитывать рост архива и свободный диск.
