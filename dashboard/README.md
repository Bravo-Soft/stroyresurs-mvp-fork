# Диспетчерская

Операторская консоль системы мониторинга Стройресурс: запустил — наблюдает —
вмешался точечно — очистил — перезапустил, вместо терминала и `docker exec`.

Реализация спецификации **«Диспетчерская: панель управления и дашборд», версия 1.1
от 26.08.2026**. Ниже — соответствие разделам спецификации, как поднять панель на
локальной машине без Docker и как проверить сценарии приёмки.

---

## 1. Что это и где лежит

Одно FastAPI-приложение на стороне mvp, порт **:5510**. Сервис живёт постоянно и
**владеет** процессом пайплайна: `main.py` запускается его подпроцессом.

| Файл | Роль |
|---|---|
| `app.py` | FastAPI: маршруты `/api/v1/*`, авторизация Bearer, светофор здоровья, сторож |
| `common.py` | Доступ к `Config`, каталоги прогонов, чтение JSON — общая база модулей |
| `supervisor.py` | Владение процессом: singleton-lock, старт/стоп/рестарт, сторож по простою (§5) |
| `metrics.py` | Агрегация метрик из файлов прогонов, ошибки по блокам, хвост лога (§8) |
| `companies.py` | Ситлист, карточка компании, сводка графа, срочная задача в Kafka (§3) |
| `purge.py` | Очистка данных компании: dry-run, выполнение, защита целей (§7) |
| `settings_store.py` | env-белый список, файл переопределений, валидация (§6) |
| `profiles_store.py` | YAML-профили сайтов: чтение/правка/удаление, приём черновика переписи |
| `journal.py` | Журнал операций: append-only JSONL (§9) |
| `static/index.html` | Пять экранов, vanilla JS, без сборки фронтенда (§2, §3) |
| `fake_pipeline.py` | Эмулятор пайплайна для репетиции сценариев без краула и LLM |
| `selftest.py` | Сквозная проверка контракта API и кодов ошибок |
| `make_demo_sitelist.py` | Устарел: ситлист переехал из Site_list.xlsx в Postgres (`site_list_db.py`) |

Панель поднимается на интерпретаторе **без зависимостей пайплайна**
(playwright / llama-index / aiohttp): её модули используют только стандартную
библиотеку плюс `fastapi`, `uvicorn`, `pydantic`, `psycopg2-binary`. Ситлист читается из
Postgres (`SITE_LIST_DSN`, таблица `public.companies`) либо, если DSN не задан, из
существующего `Site_list.xlsx`; недоступность обоих источников даёт `/companies` код 503.
Всё, что требует зависимостей пайплайна, деградирует честно (см. §5 ниже).

Данные, которые панель читает, пишет сам пайплайн — новой телеметрии не заводилось:

```
logs/runs/
  status.json              heartbeat: что происходит прямо сейчас
  control.json             команда мягкой остановки (pipeline_control.py)
  pipeline.pid             PID запущенного пайплайна
  pipeline.lock            singleton-lock Диспетчерской
  pipeline_stdout.log      stdout/stderr подпроцесса (трейсбеки при падении)
  journal.jsonl            журнал операций оператора (§9)
  <run_id>/run.json        сводка прогона
  <run_id>/companies.jsonl строка на обработанную компанию
```

## 2. API (§4)

Всё под `/api/v1`, авторизация — `Authorization: Bearer <env DASHBOARD_TOKEN>`.
Без токена в окружении сервис отвечает 503: управление отключено намеренно.

### Наблюдение

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/status` | running / stopped / stalled, PID, текущая компания, прогресс N/M, heartbeat, состояние сторожа и перезапуска |
| GET | `/runs`, `/runs/{run_id}` | История прогонов; детали + файлы отчётов прогона |
| GET | `/logs/tail?lines=&source=monitoring\|stdout` | Хвост активного лога |
| GET | `/metrics/summary` | Сводка последнего прогона (§8) |
| GET | `/metrics/companies?run_id=` | Метрики по компаниям: время по модулям, товары, страницы, нули |
| GET | `/companies` | Ситлист (для выбора подмножества) |
| GET | `/companies/{id}` | Карточка: последний результат, документы по группам, профиль (домен, наличие, черновик переписи) |
| GET | `/profiles/{domain}` | Профиль сайта для редактора: текст, версия, ошибки валидации, схема, черновик переписи |
| GET | `/companies/{id}/graph` | Сводка графа отдельным запросом — см. примечание ниже |
| GET | `/errors?run_id=` | Ошибки прогона по блокам пайплайна + время в ретраях |
| GET | `/checkpoint` | С какого места продолжится рестарт |
| GET | `/health` | Светофор: Graph DB, бот Пачки, Kafka, LLM-шлюз + индикаторы |
| GET | `/journal?limit=&action=&company_id=` | Журнал операций |

> **Смерть процесса.** Если пайплайн завершился не по команде панели (падение,
> перезагрузка хоста, kill извне), `GET /status` — его зовут UI раз в 10 с и сторож
> раз в 60 с — помечает незакрытый прогон `aborted` (`aborted_by: pipeline-exited`),
> пишет в журнал `pipeline.exited` с PID и кодом выхода (после рестарта панели код
> неизвестен — `null`) и при аварийном завершении шлёт алерт в Пачку
> (`WATCHDOG_ALERT_PACHCA`). Штатное завершение тоже попадает в журнал с `result: ok`.

> **Почему сводка графа — отдельный эндпоинт.** Backend отвечает на
> `companies/get` порядка **15 секунд**. Если тянуть её внутри карточки, экран
> висит все 15 с. Карточка отдаётся за ~0,3 с с меткой `graph.pending`, а UI
> дотягивает блок графа вторым запросом. Форсировать старое поведение —
> `GET /companies/{id}?with_graph=true`.

### Управление

| Метод | Путь | Тело | Поведение |
|---|---|---|---|
| POST | `/pipeline/start` | `{"mode":"full"\|"urgent-only","resume":true,"company_ids":[…]}` | 409, если экземпляр уже работает |
| POST | `/pipeline/stop` | `{"force":false}` | Мягкая — через `control.json`; `force` — снятие дерева процессов |
| POST | `/pipeline/restart` | `{"mode":"full","company_ids":[…]}` | Ставится в фон: stop → ожидание → start с `resume:true` |
| POST | `/companies/{id}/crawl` | — | Задача в Kafka `urgent_tasks` — тот же путь, что у бота |

### Настройки и очистка

| Метод | Путь | Тело |
|---|---|---|
| GET | `/settings` | — |
| PUT | `/settings` | `{"values":{"MAX_CONCURRENT_PAGES":"12"}}` |
| POST | `/companies/{id}/purge/dry-run` | `{"sources":["temp","documents","graph"]}` |
| POST | `/companies/{id}/purge` | `{"sources":[…],"confirm_company_id":"<id>"}` |

### Профили сайтов

Редактор сырого YAML на карточке компании (кнопка «Профиль сайта»). Файл —
`<PROFILES_DIR>/<домен>.yaml`; текст сохраняется как набран (комментарии и порядок
ключей живут), проверка — тем же `site_profiles.profile_from_dict`, что и в пайплайне,
плюс совпадение `domain` с именем файла и компилируемость regex в `sections.*_patterns`.
Оптимистическая блокировка: `version` = sha1 содержимого, PUT с чужой версией → 409.
Пайплайн перечитывает каталог профилей перед каждой компанией
(`ProfileResolver.reload_if_changed`), поэтому правка применяется **со следующей
компании бегущего прогона**, а не при следующем старте, как настройки §6.

| Метод | Путь | Тело | Коды |
|---|---|---|---|
| GET | `/profiles/{domain}` | — | 200 и при отсутствии файла (`exists:false`) |
| POST | `/profiles/{domain}/validate` | `{"text":"…"}` | 200 `{valid:true}`, 422 `{detail, errors:[…]}` |
| PUT | `/profiles/{domain}` | `{"text":"…","expected_version":"<sha>"\|null}` | 409 версия разошлась, 422 ошибки схемы |
| DELETE | `/profiles/{domain}` | `{"confirm_domain":"<домен>"}` | 404 нет файла, 409 подтверждение не совпало |
| POST | `/profiles/{domain}/accept-draft` | `{"expected_version":…}` | 404 нет черновика, 409 уже принят |

Приём черновика переписи (`<PROFILES_DRAFTS_DIR>/<домен>.yaml`, пишет `census_collector`
при `CENSUS_ENABLED`): отбрасывается `census_evidence`, `source: census` → `mixed`,
`profile_version` = текущая на диске + 1; файл черновика остаётся как след переписи.
Журнал: `profile.create` / `profile.update` / `profile.delete` / `profile.accept_draft`
с доменом, размером, версией и изменёнными верхнеуровневыми ключами — тела файла в
журнале нет.

### Коды (§9)

401 без/с неверным токеном · 503 если `DASHBOARD_TOKEN` не задан или нет PyYAML для
записи профилей · 409 повторный `start`, `stop` незапущенного, очистка компании в работе,
несовпавшее подтверждение, версия профиля разошлась · 404 несуществующие прогон,
компания, профиль или черновик · 400 кривой id/домен, служебное имя `_*.yaml` ·
422 неизвестный режим, параметр вне белого списка, неверный тип значения, неизвестный
источник очистки, невалидный профиль.

## 3. Запуск на локальной машине (без Docker)

Панели достаточно интерпретатора с `fastapi`, `uvicorn`, `pydantic`, `psycopg2-binary`.
На этой машине подходит `py -3.10`; `mvp/venv` непригоден (создан в чужом профиле).
Ситлист берётся из Postgres при наличии `SITE_LIST_DSN` в `mvp/.env`; без DSN панель
читает тот же `Site_list.xlsx`, что и текущий пайплайн. `config.py` подхватывает `.env`
через `load_dotenv`.

### 3.1. Почему нужны переменные каталогов

Дефолты путей в `config.py` — серверные (`/home/user/stroy-resurs/mvp/...`). На
Windows они разворачиваются в `C:\home\user\...`, и данные растекаются мимо проекта.
Поэтому `config.py` теперь читает пути из окружения (`LOGS_DIR`, `BASE_DIR`, …), а
дефолты остались прежними — на сервере поведение не меняется.

### 3.2. Быстрый старт

Готовый скрипт `dashboard/_run_local.sh` выставляет все переменные на каталоги
внутри `mvp` и поднимает панель:

```bash
# из каталога mvp (Git Bash); SITE_LIST_DSN должен быть в mvp/.env
./dashboard/_run_local.sh
```

PowerShell — через шаблон `dashboard/local.env.example`:

```powershell
Copy-Item dashboard\local.env.example dashboard\local.env   # заменить <MVP> и токен
Get-Content dashboard\local.env | Where-Object { $_ -match '^[A-Z]' } | ForEach-Object {
    $k, $v = $_ -split '=', 2; Set-Item -Path "Env:$k" -Value $v }
py -3.10 -m uvicorn dashboard.app:app --host 127.0.0.1 --port 5510
```

Открыть <http://127.0.0.1:5510/>, ввести токен `DASHBOARD_TOKEN`: из окружения, иначе
из `mvp/.env`, и только если его нет нигде — `_run_local.sh` подставляет `test-token-local`.

### 3.3. Что запускает кнопка «Старт»

По умолчанию — `main.py`, то есть настоящий прогон: Playwright, LibreOffice,
LLM-шлюз, часы работы. Для репетиции сценариев управления это не нужно, поэтому
есть эмулятор:

```
PIPELINE_CMD=dashboard/fake_pipeline.py
```

Эмулятор ведёт себя как `main.py` с точки зрения панели: пишет те же файлы через
`run_recorder`, так же читает команду мягкой остановки, умеет изображать нулевые
компании, ошибки и зависание. В проде `PIPELINE_CMD` не задают.

| Переменная | Что делает |
|---|---|
| `FAKE_SECONDS_PER_COMPANY` | Длительность «обработки» компании (по умолчанию 6 с) |
| `FAKE_ZERO_EVERY` | Каждая N-я компания даёт ноль товаров |
| `FAKE_FAIL_EVERY` | Каждая N-я компания завершается ошибкой |
| `FAKE_HANG_AFTER` | После N-й компании перестать обновлять heartbeat (проверка сторожа) |

## 4. Проверка

### 4.1. Контракт API

```bash
py -3.10 dashboard/selftest.py --token test-token-local           # только чтение
py -3.10 dashboard/selftest.py --token test-token-local --write   # + старт/стоп
```

Проверяются все эндпоинты §4, коды ошибок §9, отсутствие утечки секретов и
fail-open поведение §2. Текущий результат на этой машине — **48 проверок, 0 сбоев**.

### 4.2. Сценарии приёмки (§10)

**Этап 1 — наблюдение.** Открыть «Обзор» во время прогона: статус, компания N из M,
% нулевых, медианное время сайта, ошибки за сутки. Данные обновляются раз в 10 с
(требование §10 — отставание не более 30 с). Выключить backend или удалить файл
метрик — страница не ломается, блок показывает «нет данных».

**Этап 2 — управление.**

```bash
# стоп -> рестарт без потери прогресса
curl -X POST -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
     -d '{"mode":"full","resume":true}' http://127.0.0.1:5510/api/v1/pipeline/start
curl -X POST … -d '{"force":false}'  …/pipeline/stop     # дозавершит компанию + чекпоинт
curl -X POST … -d '{"mode":"full"}'  …/pipeline/restart  # продолжит с чекпоинта
curl -X POST … -d '{"mode":"full","resume":true}' …/pipeline/start   # -> 409, singleton
```

**Зависание и сторож.** Поднять панель с `FAKE_HANG_AFTER=2` и
`COMPANY_IDLE_TIMEOUT_SECONDS=60`, запустить прогон. Через минуту `GET /status`
отдаёт `state: "stalled"`, ещё через проход сторожа (раз в 60 с) появляется
`watchdog.last_event` и запись `watchdog.stalled` в журнале. С
`WATCHDOG_ALERT_PACHCA=true` уходит алерт в Пачку, с `WATCHDOG_AUTORESTART=true`
выполняется мягкий перезапуск с чекпоинта.

**Этап 3 — очистка.** Экран «Компания» → «Очистить данные…»: dry-run показывает
счётчики по трём источникам, кнопка удаления разблокируется только после ввода id
компании, после выполнения отчёт сверяется с dry-run, всё пишется в журнал.

**Этап 4 — профиль сайта.** Экран «Компания» → «Профиль сайта»: открывается YAML
(или заготовка для нового файла), «Проверить» на битом тексте даёт список ошибок по
полям, «Сохранить» пишет файл и обновляет версию, сохранение со старой версией из
второй вкладки → 409, «Удалить…» разблокируется только после ввода домена. При
черновике переписи — блок «Принять черновик». Изменение видно следующей компании
бегущего прогона (строка «Профиль сайта: <домен> vN» в логе).

### 4.3. Что проверено на этой машине

| Сценарий | Результат |
|---|---|
| Контракт API (48 проверок) | пройдено |
| Полный прогон 8 компаний через эмулятор | 6 успешно, 2 с ошибками, 2 нулевых (25 %) |
| Классификация ошибок по блокам | «Таймаут краулера» → Краулер, «SGR вернул пустой ответ» → ИИ-извлечение |
| Singleton: повторный старт | 409 |
| Мягкая остановка | процесс завершился, прогон помечен aborted |
| Жёсткая остановка | дерево процессов снято, прогон финализирован как aborted |
| Зависание → сторож | `stalled` через 60 с, событие и запись в журнале через 120 с |
| Режим urgent-only | стартует с `--urgent-only`, прогресс 0/0, мягкая остановка работает |
| Очистка temp + documents | dry-run 6 и 4 файла = фактически удалено; реальные каталоги и архивы не тронуты |
| Настройки: PUT → файл переопределений → окружение подпроцесса | дифф «было → стало» в журнале, секреты не выводятся |
| Светофор здоровья | Graph DB, бот, Kafka — живы; LLM-шлюз недоступен (туннель закрыт) |

## 5. Чего пока нет и почему

**Удаление компании из графа (§7, источник `graph`).** Требует нового эндпоинта на
NestJS-backend, которого нет, и упирается в открытый вопрос 11.1 спецификации:
физически удалять все версии или закрывать валидность текущей. Клиентская сторона
готова целиком: dry-run честно считает объекты компании через существующий
`companies/get`, а само удаление возвращает `supported: false` с объяснением.
Включение — одна константа `GRAPH_DELETE_PATH = '/delete'` в `purge.py`.

**Параметры §6.** В текущей сборке пайплайна все параметры §6 читаются
`Config.load_from_env` (`MAX_CONCURRENT_FILE_DOWNLOADS`, `PRODUCT_MIN_TEXT`,
`PIPELINE_STREAMING_ENABLED`, `PIPELINE_PAGE_WORKERS`, `CENSUS_ENABLED`,
`COMPANY_IDLE_TIMEOUT_SECONDS`) и включены в белый список экрана «Настройки».
Блок «нет в этой версии» (`settings_store.NOT_IN_THIS_BUILD`) пуст; принцип прежний —
белый список строится из того, что реально читает `Config.load_from_env`.

Корректировки от 07.09.2026: из белого списка убраны `AI_TUNNEL_API_KEY` (AI Tunnel
больше не используется) и `VECTOR_DB_ENABLE` / `VECTOR_DB_PATH` (векторная БД упразднена,
остался только граф); добавлены `LLM_REQUEST_DELAY_SECONDS` (пауза между запросами к LLM,
`config.llm_request_delay_seconds`, применяется в `AITunnelClient._make_request_with_retry`),
`MAX_PAGES_PER_SITE` и `MAX_PRODUCT_PAGES_PER_SITE` (лимиты страниц на сайт; теперь
читаются из env в `load_from_env`). У каждого параметра есть описание на русском —
`selftest.py` это проверяет. На экране «Обзор» убрана плитка «Стоимость прогона»
(инференс бесплатный), на экране «Компания» блок «Документы» показывает четыре группы
файлов компании на диске: Документы, Сертификаты, Инструкции, Прайс-листы
(`companies.documents_summary`, папки `Documents/Certificates/Instructions/Price_lists`).

**Алерты профилей (§8).** Блок читает `<config.profile_metrics_dir>/<domain>/*.json`
(по умолчанию `Base/profile_metrics`, пишет `RunMetricsCollector` в конце каждой
компании). Пока каталога нет — блок отдаёт «нет данных».

**Сторож панели и сторож пайплайна.** Внутри пайплайна работает свой сторож D101
(`pipeline_orchestrator._process_company_watchdogged`): молчание лога дольше
`COMPANY_IDLE_TIMEOUT_SECONDS` — компания бросается, пул браузеров пересоздаётся,
прогон идёт дальше (в `companies.jsonl` запись со статусом `abandoned_idle`). Пульс
`status.json` обновляется тем же признаком — записями в лог (`run_recorder.install_heartbeat`),
поэтому статус «завис» у панели наступает по порогу `COMPANY_IDLE_TIMEOUT_SECONDS +
WATCHDOG_GRACE_SECONDS` (по умолчанию 1800 + 300 с) и означает зависание всего процесса,
а не одной компании.

**Краул по id при отсутствии `aiokafka`.** Клиент Kafka — зависимость пайплайна, а
не панели. Если его нет в окружении Диспетчерской, `POST /companies/{id}/crawl`
отвечает 503 с объяснением, а не теряет задачу молча. Альтернатива без Kafka —
запуск подмножества компаний галочками в диалоге «Старт».

## 6. Развёртывание на сервере

1. `DASHBOARD_TOKEN` должен быть задан в `mvp/.env` (обязательно, иначе панель отвечает 503).
2. `uvicorn` и `psycopg2-binary` добавлены в `requirements.txt`; образ нужно пересобрать.
3. Корневой `docker-compose.yml` уже запускает `mvp` как Диспетчерскую:
   `python -m uvicorn dashboard.app:app --host 0.0.0.0 --port 5510`. Пайплайн
   панель запускает сама как дочерний процесс по кнопке «Старт».
4. Порт опубликован только на `127.0.0.1:5510`; для внешнего доступа используйте
   HTTPS reverse proxy или SSH-туннель, а не публичный Docker port.
5. Переменные каталогов на сервере можно не задавать — сработают серверные дефолты
   `config.py`; `PIPELINE_CMD` тоже не задавать, чтобы кнопка «Старт» запускала
   настоящий `main.py`.
6. Настройки из экрана «Настройки» хранятся в host-volume
   `mvp_directories/dashboard/settings_overrides.env` и переживают пересоздание
   контейнера. `dashboard/local.env` игнорируется Git и предназначен только для dev.
7. Первое, что проверить на сервере после выкладки: мягкий стоп живого прогона
   (`POST /pipeline/stop`) — в `monitoring.log` появляется «Получена команда мягкой
   остановки», в `Base/processing_checkpoint.json` стадия `stopped_by_admin`.
